실험 1. WORKFLOW

키워드 하나로 HR 인사이트 워크플로우 설계

2026-07-14
WORKFLOW

HR·리더십 키워드 하나를 입력하면 전략 인사이트 자료를 정리하고, Slack Canvas 반영 → 지정 채널 알림 → 뉴스레터 초안과 이미지·컬러·해시태그 제안까지 이어지는 워크플로우를 만들었습니다.

QUESTION   질문

반복되는 리서치·구조화·Slack 공유·콘텐츠 제안 과정을 재사용 가능한 스킬로 만들면, 결과 편차를 줄이고 팀에 더 빠르게 공유할 수 있을까?

CONTEXT   문제 상황

디자인 외에도 HR·리더십 인사이트 자료를 만들어 팀에 공유하는 업무를 자원해 맡고 있었습니다. 키워드가 정해질 때마다 리서치 → 구조화 → Slack Canvas 반영 → 채널 알림 → 뉴스레터 초안 제안까지 반복했고, 포맷·톤·출처 기준이 조금씩 달라지는 문제가 있었습니다. 반복 작업을 규칙으로 고정해 지속 가능하고 이관 가능한 형태로 만들고 싶었습니다.

TRY   시도

• 실제 키워드 ‘Radical Integrity’로 전체 흐름을 처음부터 끝까지 테스트했습니다
• HBR·Gallup·McKinsey·Russell Reynolds 등 신뢰할 수 있는 아티클과 검증된 통계만 수집했습니다
• 강조 부호 제거, 통계 옆 출처 링크, 검색 결과 URL 제외 등 작성 규칙을 고정했습니다
• 최신 항목이 Slack Canvas 상단에 쌓이도록 반영하고, 초안 승인 후 채널 알림이 나가도록 구성했습니다
• CANVAS_ID·NOTIFY_CHANNEL·ORG_NAME·SIGNATURE 등 개인·조직 값을 설정값으로 분리하고, insight-cowork SKILL.md로 문서화해 패키징했습니다

FRICTION   막힌 지점

검색 결과 페이지 URL은 문단의 근거로 쓰기에 부정확했고, Canvas 편집 액션도 문서 설명과 실제 동작이 달라 중복이 생기는 지점이 있었습니다. 또 캔버스 ID·채널·발신 명의 같은 값을 하드코딩하면 보안과 재사용성이 떨어졌습니다.

CHANGE   바꾼 점

검색 결과가 아니라 문단의 주장과 가장 맞는 특정 아티클을 인라인 출처로 배치했습니다. Canvas 반영 전에는 현재 section_id를 확인하고, 실행 후 중복·손실을 다시 검증하도록 했습니다. 개인·조직 값은 설정값으로 분리하고, Canvas 반영과 알림은 반드시 초안 승인 후 실행하도록 규칙화했습니다.

LEARNED   배운 점

도구의 동작은 문서 설명만 믿기보다 실제 실행 결과를 다시 확인해야 했습니다. 출처도 “검색됨”에서 끝나는 것이 아니라 문단의 주장과 가장 잘 맞는 특정 아티클을 골라야 신뢰가 생겼습니다. 개인값을 설정값으로 분리하고, 승인 절차와 문체 규칙까지 포함해야 다른 사람도 재사용할 수 있는 스킬이 된다는 점을 배웠습니다.

실험 2. DESIGN OPS

디자인 요청을 자동으로 관리하는 트래커 구축

2026-07-21
DESIGN OPS

Claude와 Slack·Notion 커넥터를 연결해 접수·분류·누락 점검·기록·회고까지 이어지는 디자인 요청 트래커를 구축했습니다. 이후 Obsidian을 연결하고 디자인 작업 대시보드도 구성했습니다.

QUESTION   질문

디자인 요청을 자동으로 정리하고, 필요한 정보를 빠짐없이 확인하며, 완료 후 회고까지 연결할 수 있을까?

CONTEXT   문제 상황

팀별 디자인 요청은 많고 작업 기간은 짧아, Slack으로 들어오는 일을 처리하는 데 급급했습니다. 분기별 회의 때는 완료한 업무와 성과를 다시 정리해야 했고, 요청 내용과 정량 지표를 수기로 파악하다 보니 정확도가 떨어졌습니다. 일을 많이 해도 성과를 뒷받침할 근거를 준비하는 데 피로가 커, 기록과 회고를 자동으로 남길 필요가 있었습니다.

TRY   시도

• Slack에서 디자인 요청을 수집하고 매일 아침 알림을 받도록 구성했습니다
• Notion에는 트래커 DB와 대시보드를 만들었습니다
• Obsidian에는 플레이북·요청 노트·회고 기록을 쌓았습니다
• Gmail은 브리핑 백업 알림용으로 연결했지만, Slack으로 충분해 이후 중단했습니다

FRICTION   막힌 지점

초기에는 자연어 프롬프트를 너무 길게 작성해 오차 범위가 커졌고, Claude 토큰도 많이 소모해 구현 속도가 늦어졌습니다. 또 Notion 무료 버전의 API 사용 한계 때문에 원하는 수준까지 확장하지 못하고 일부 기능을 잠시 중단했습니다.

CHANGE   바꾼 점

Slack 요청부터 완료까지의 상태와 소요 시간을 추적해 Notion 대시보드에 자동 기록했습니다. 업무 분류·요청자·상태·마감 희망일·배정 스킬·누락 자료를 구조화하고, 완료 후 회고 6항목도 함께 축적했습니다. 미완료·마감 임박·카테고리별 누적·분기·연간 리뷰를 확인하는 라이브 대시보드를 만들고, 완료 이모지를 감지해 상태 변경과 회고 알림까지 이어지도록 구성했습니다. Slack은 입력, Notion은 상태 저장, Obsidian은 규칙과 회고 저장으로 역할을 나눴습니다.

LEARNED   배운 점

반복 업무 자체보다 내가 반복해서 불편함을 느끼는 지점을 먼저 알아차리는 것이 중요했습니다. Claude도 단순한 도구보다 역할과 규칙이 명확한 협업자로 설정할수록 결과 품질이 높아졌고, 외부 저장소에 규칙과 기록을 남기면 세션이 바뀌어도 같은 기준으로 업무를 이어갈 수 있었습니다.

CONTEXT   문제 상황

교육 서비스 회사이자 연구소로서 전문 자료를 꾸준히 발굴하고, 현업의 전문성과 안목을 높여 제안서·고객사 소통·세미나에 활용할 필요가 있었습니다. 특히 B2B팀은 대기업 고객을 상대하고 세미나도 자주 열어 전문 지식이 중요하지만, 아직 AX 활용에 익숙하지 않아 자료를 찾고 정리하는 데 시간이 많이 들었습니다.

TRY   시도

Zotero → Codex MCP → 구조화 → Notion → 실무 활용의 흐름을 설계했습니다.

FRICTION   막힌 지점

처음에는 MCP 서버를 실행하는 것과 실제 앱에서 MCP 도구를 연결해 사용하는 것을 같은 단계로 이해해 시행착오가 있었습니다.

CHANGE   바꾼 점

직접 만든 배경음악

MusicGen으로 다섯 가지 음악 시안을 만들고 멜로디 버전을 선택했습니다. Python으로 반복 구간과 변주를 만들고, FFmpeg로 음량을 다듬어 영상에 적용했습니다.

GitHub에 업로드한 WAV · 음원 파일 열기

음악 제작 과정 자세히 보기

생성 · MusicGen facebook/musicgen-small을 Python transformers + torch로 로컬 CPU에서 실행했습니다. 100 BPM 재즈 힙합 연주곡을 요청하고, seed 41로 약 14초 길이(max_new_tokens=700)의 음악을 생성했습니다. 한 번에 긴 영상을 만들면 메모리 부족(OOM)이 발생해 짧게 생성했습니다.

프롬프트 · lo-fi jazz hop beat with a catchy flute and violin melody, chopped soul sample, punchy drums, deep bass, bright and energetic, 100 bpm, instrumental

시안 선택 · hiphop 2종, melodic 2종, 비트·멜로디 혼합 1종 등 총 5개를 비교해 candidate-melodic-2.wav를 선택했습니다.

후처리 · Python + NumPy(dj2.py)로 14초 클립을 세 구간으로 확장했습니다. 저역 필터 스윕, 되감기·스터터, 고역 필터 드롭, 바이닐 노이즈와 클릭을 더했습니다.

음량 보정 · FFmpeg acompressor 2단(−28dB ratio 6 → −20dB ratio 3), loudnorm(I=−15, TP=−2, LRA=7), alimiter(0.95)를 적용했습니다. 크로스페이드는 1.5초에서 0.5초로 줄였습니다.

제작 기록 · 최종 트랙 41.2초, 48kHz 스테레오, −16.0 LUFS, True Peak −2.4 dBTP. 영상에는 약 29.3초를 사용했습니다. 현재 GitHub 파일의 기술 메타데이터는 별도로 대조하지 못했습니다.
